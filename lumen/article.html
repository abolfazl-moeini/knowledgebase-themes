Authentication

Choose the right authentication method for your integration — from quick scripts to enterprise SSO.

15 min read Updated 3 days ago Edit on GitHub

Lumen supports four authentication strategies. Pick the one that fits your use case — they can be combined within a single workspace, with per-key scopes and rate limits.

Pick the smallest scope that works

Never use a master key in client-side code or shared scripts. Create a scoped key per integration and rotate it on a schedule.

API keys

The fastest path. Generate a key in the dashboard, send it as a bearer token, and you're authenticated. Best for server-to-server and CI jobs.

cURL 
curl https://api.lumen.dev/v1/projects \
  -H "Authorization: Bearer sk_live_your_api_key_here" \
  -H "Content-Type: application/json"

Keys are prefixed so you can spot them in logs: sk_live_… for production, sk_test_… for the sandbox. The two prefixes are never interchangeable, which keeps test data isolated even by accident.

Rotating keys

You can have up to 10 active keys per workspace. To rotate without downtime, create the new key first, deploy code that uses both, then revoke the old one. Lumen supports a brief overlap window of 24 hours during which both keys resolve to the same principal.

OAuth 2.0

When you need to act on behalf of a user — for example, building a third-party app that connects to a user's Lumen workspace — use OAuth 2.0 with PKCE. We support the authorization code flow and the device flow for input-constrained clients.

JavaScript 
const token = await lumen.oauth.exchange({
  grant_type: 'authorization_code',
  code: 'auth_code_here',
  redirect_uri: 'https://yourapp.com/callback',
  code_verifier: storedVerifier,
});

console.log(token.access_token);
// → "ya29.a0AfH6SMB..."

Required scopes

Request only the scopes you need. The user will see exactly which permissions your app is asking for. You can request additional scopes later via the incremental authorization flow — no need to re-consent to everything.

ScopeAllows
read:projectsList and read project metadata
write:projectsCreate, update, archive projects
read:eventsSubscribe to webhook topics
manage:teamInvite users, change roles

Service accounts with JWT

For long-lived server workloads that need to assume a specific identity — scheduled jobs, event-driven workers, data pipelines — issue a short-lived JWT signed with a service account's private key. Tokens are valid for up to 1 hour and refresh automatically.

Keep your private key out of the repo

Load the signing key from your secrets manager at boot. If a private key is ever committed, revoke the service account immediately — Lumen will detect and alert on any new JWTs signed with the leaked key.

Single sign-on (SSO)

Enterprise workspaces can enforce SSO with any SAML 2.0 or OIDC provider — Okta, Azure AD, Google Workspace, OneLogin, and others. When SSO is enforced, personal API keys and passwords are disabled for the workspace.

Configuration lives in Workspace settings → Authentication → SSO. You'll need workspace admin permissions to make changes. After enabling, the first 24 hours are a soft-enforcement window where users can still fall back to other methods — useful for migration.

Just-in-time provisioning

Pair SSO with SCIM to provision users automatically. New users appear in your workspace the first time they sign in. Roles are mapped from your IdP's group membership.

Best practices

  • Use the smallest scope. Read-only keys for analytics, write keys for automation, admin keys only for break-glass.
  • Rotate on a schedule. Every 90 days for human-owned keys, every 30 days for CI keys.
  • Audit regularly. The Key activity view shows every call a key has made in the last 90 days.
  • Never put a key in client code. Use a server-side proxy for browser or mobile apps — call it from your backend, not from the user.
  • Fail closed on expiry. Treat 401 as a hard stop, not a retry. A token that has expired should never be silently refreshed in a hot loop.

Test with the sandbox

Use sk_test_… keys against https://api.sandbox.lumen.dev to test your integration without touching production data. The sandbox is reset nightly and isolated from your live workspace.

Troubleshooting

Most auth failures fall into three buckets:

  1. 401 Unauthorized — the token is missing, malformed, or revoked. Double-check the prefix, the workspace, and the rotation status.
  2. 403 Forbidden — the token is valid but doesn't have the scope for this resource. Request an upgraded key or expand the OAuth grant.
  3. 429 Too Many Requests — you're being rate-limited. Back off, respect the Retry-After header, and consider a token bucket on your side.

For anything else, the Auth debug endpoint returns a structured trace of the failed request — useful for support tickets.
