Authentication, considered

Choose the right authentication method for your integration. The four methods below are not interchangeable — each is a fit for a particular shape of work.

read time 15 min updated 3 days ago 4 runnable snippets

The first question to ask about authentication is rarely "which method?" — it is "what is this code on behalf of whom?" A script in your CI is a different animal from a button in someone else's browser. The four methods below are tools, each shaped to a particular hand.

Pick the smallest scope that works

Never use a master key in client-side code. Create a scoped key per integration and rotate it on a schedule.

API keys #

The fastest path. Generate a key in the dashboard, send it as a bearer token, and you're authenticated. Best for server-to-server and CI jobs.

bash list-projects.sh — first authenticated request 
# list all projects in the workspace
curl https://api.example.dev/v1/projects \
  -H "Authorization: Bearer sk_live_your_api_key_here" \
  -H "Content-Type: application/json"

Keys are prefixed so you can spot them in logs: sk_live_… for production, sk_test_… for the sandbox. The two prefixes are never interchangeable, which keeps test data isolated even by accident.

Rotating keys

You can have up to 10 active keys per workspace. To rotate without downtime, create the new key first, deploy code that uses both, then revoke the old one. The platform supports a 24-hour overlap window during which both keys resolve to the same principal.

OAuth 2.0 #

When you need to act on behalf of a user — building a third-party app that connects to a user's workspace — use OAuth 2.0 with PKCE. We support the authorization code flow and the device flow for input-constrained clients.

javascript oauth.js — exchange the auth code 
import { Example } from '@example/sdk';

const token = await example.oauth.exchange({
  grant_type: 'authorization_code',
  code: 'auth_code_here',
  redirect_uri: 'https://yourapp.com/callback',
  code_verifier: storedVerifier,
});

console.log(token.access_token);

Required scopes

Request only the scopes you need. The user will see exactly which permissions your app is asking for. You can request additional scopes later via the incremental authorization flow.

Service accounts with JWT #

For long-lived server workloads that need to assume a specific identity — scheduled jobs, event-driven workers, data pipelines — issue a short-lived JWT signed with a service account's private key. Tokens are valid for up to 1 hour and refresh automatically.

python issue_jwt.py — sign a service-account token 
import time, jwt
from example import ServiceAccount

sa = ServiceAccount.from_env()
token = sa.issue_token(
    subject="svc-prod-worker",
    scope=["read:projects", "write:events"],
    ttl=3600,
)
print(token)
Keep your private key out of the repo

Load the signing key from your secrets manager at boot. If a private key is ever committed, revoke the service account immediately.

Single sign-on (SSO) #

Enterprise workspaces can enforce SSO with any SAML 2.0 or OIDC provider — Okta, Azure AD, Google Workspace, OneLogin, and others. When SSO is enforced, personal API keys and passwords are disabled for the workspace.

Configuration lives in Workspace settings → Authentication → SSO. You'll need workspace admin permissions to make changes. After enabling, the first 24 hours are a soft-enforcement window where users can still fall back to other methods — useful for migration.

Troubleshooting #

Most auth failures fall into three buckets:

  1. 401 Unauthorized — the token is missing, malformed, or revoked.
  2. 403 Forbidden — the token is valid but doesn't have the scope for this resource.
  3. 429 Too Many Requests — you're being rate-limited. Respect the Retry-After header.
bash debug.sh — get a structured trace of a failed call 
curl -X POST https://api.example.dev/v1/_debug/auth \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -d '{"request_id": "req_4eC39HqLyjWD"}'
