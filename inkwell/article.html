Authentication, considered

Choosing the right strategy is a quiet act of care. The four methods below are not interchangeable — each is a fit for a particular shape of work.

Written by the editors First published 14 March 2026 Last revised 2 days ago

The first question to ask about authentication is rarely "which method?" — it is "what is this code on behalf of whom?" A script that runs in your CI system is a different animal from a button in someone else's browser, and the answer changes everything that follows. The four methods in this essay — API keys, OAuth 2.0, signed JWT, and single sign-on — are not rungs on a ladder. They are four tools, each shaped to a particular hand.

What follows is a long, deliberate walk through when to use which, and the small habits that make each one safer to live with. We will not assume you have read the quickstart; we will not assume you haven't. We will simply go slowly, and trust you to read at the speed that suits you.

Of API keys

The API key is the oldest, simplest method we support, and the one most often misused. It is a bearer token: whoever holds it is, in our system's eyes, the principal that issued it. This is convenient and dangerous in equal measure, and the entire art of using keys well is the art of narrowing who can hold them.

curl — make your first authenticated request 
curl https://api.inkwell.dev/v1/projects \
  -H "Authorization: Bearer sk_live_your_api_key_here" \
  -H "Content-Type: application/json"

Two habits, in particular, will save you. The first is to give every key a name and a scope, so that when a key is found in a log file you can tell at a glance what it is for. The second is to rotate them. Not because keys are fragile, but because keys leak. A key that has been in a single place for two years is a key that has been copy-pasted, screenshotted, or set as a default somewhere. Rotate them the way you would change the locks on a house you actually live in.

Rotation, without downtime

You can have up to ten active keys per workspace, and during a rotation both keys resolve to the same principal for a window of twenty-four hours. This is the small gift that makes zero-downtime rotation possible: create the new key, deploy code that uses both, revoke the old one. The brief overlap is the seam, and it is a seam you can plan around.

On acting on behalf of a user

When your code needs to do something in a user's workspace — read their projects, send a message on their behalf, list their team's billing history — the API key will not do. The key is for you; the user is, at this moment, a different principal. The protocol we use to bridge this is OAuth 2.0, with PKCE for the public clients that need it.

"The user must always be able to see exactly which permissions you are asking for, and revoke them in a single click."

— A principle from the first edition, still binding.

The grant types we support — authorization code, device, and refresh — are each suited to a different shape of client. A server-side web app uses the authorization code flow. A CLI tool installed on someone's laptop uses the device flow. A long-running integration uses the refresh flow to swap a short-lived access token for a new one, invisibly.

The smallest scope that works

When you ask for scopes, ask for the smallest set that lets you do the work in front of you. The user will see exactly which permissions you are requesting; if the list is long and unfamiliar, they will say no, and they will be right to. You can always ask for more later, in a follow-up consent flow. The reverse is not true.

A field note

Two-thirds of the support tickets we receive about authentication turn out to be the same problem: a developer requested a scope they didn't need, then tried to use it on a route whose required scope was different. The error message is identical in both cases. Read the route's required_scopes first.

Service accounts and the signed JWT

For workloads that need to assume a stable, long-lived identity — scheduled jobs, event-driven workers, nightly pipelines — the signed JWT is the right tool. A short-lived token, signed by a private key you hold, presented on every request. The window of exposure is at most one hour; the key never leaves your infrastructure.

A service account is not a user. It has no password, no inbox, no browser. It has a key, a name, and a purpose. Treat it accordingly.

The habits here are slightly different. A service account's private key should live in a secrets manager, not in the repository. It should be loaded at boot, not interpolated at request time. And it should be rotated, not by replacing the key in place, but by issuing a new account, migrating the workload, and retiring the old one. The discontinuity is a feature: it forces you to know what depends on the identity, and to migrate deliberately.

Single sign-on, in the enterprise

For workspaces of any size, single sign-on is not a luxury. It is the only way to be sure that the person in the chair is the person you think they are, and that the right person has been told, in your identity provider, that they have the right to be there. We support SAML 2.0 and OIDC; the choice between them is usually driven by what your IdP supports, not by what we prefer.

When SSO is enforced, personal API keys and passwords are disabled for the workspace. This is the point of the enforcement. The first twenty-four hours are a soft window — a period in which users can fall back to other methods, and your team can find the integrations that depended on them. After that, the windows are closed. Plan the migration accordingly.

Just-in-time provisioning

Pair SSO with SCIM, and new users will appear in your workspace the first time they sign in. Their roles are mapped from group membership in your IdP. Off-boarding becomes a single action: remove them from the group, and the next time our SCIM endpoint asks, they are gone. This is the quietest, most reliable kind of off-boarding there is.

Small habits

We end where we began, with the question of care. The four methods above are not difficult to use. They are, however, easy to use badly — to leave a key in a place it should not be, to grant a scope broader than the work requires, to skip rotation because the calendar is full. The habits that prevent this are unglamorous: a quarterly review of every active key, an audit log of who used what, a small ritual of rotation.

  • Read the route's required_scopes before you write the code that calls it.
  • Treat the API key as you would treat a passport: a thing that identifies a principal, to be shown and not left on a counter.
  • For service accounts, prefer rotation by replacement over rotation in place. The discontinuity is the point.
  • When you set up SSO, set up SCIM at the same time. They are half of one thing.
  • Audit, on a schedule you will actually keep.

None of this is interesting. All of it is necessary. And the difference between a workspace that is easy to live with and one that is a chronic source of small panics is, more often than not, the cumulative weight of these habits.
